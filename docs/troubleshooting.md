# Troubleshooting

`journalctl -b -u geforce-bar1-resize` is the authoritative log; `sudo geforce-bar1-resize check` shows every check
and the plan per card.

| Journal or symptom | Meaning and fix |
|---|---|
| `VRAM unknown (driver never seen this card)` | The NVIDIA driver has not bound the card since the install. Boot once with the driver; the record unit stores VRAM (`RECORD_DELAY`, 60 s by default, after the bind) and the next boot enlarges BAR1. Or set `size=` for the card. |
| BAR1 smaller than VRAM after a VRAM change or a card swap: the boot log shows `VRAM <V> MiB (record)` with the old size | The record unit runs no `nvidia-smi` for a card the record already holds at that address with the same ids (`record: <BDF> <ids> VRAM <V> MiB already recorded; nvidia-smi not run`), so a memory mod, or a swap for a card with the same ids and other VRAM, keeps the old size. Run `sudo geforce-bar1-resize record` (without an address it queries every card again), then reboot. Or set `size=` for the card. |
| After replacing or moving a card | A card with other ids at an address has no usable record there: the boot logs `<BDF> VRAM record is for <old ids>, the card is <new ids>; record ignored`, then `VRAM unknown`, and leaves it stock. A card at an address without a record gets `VRAM unknown` too. Once the driver has bound it, the record unit stores its VRAM (after `RECORD_DELAY`) and the next boot enlarges it; `size=` for the card (or a global `SIZE=`) skips the wait. Same ids but other VRAM: the row above. The driver option file written for the old card still names the address, so at the first boot the new card gets that card's `RMForceStaticBar1=0`; when the record unit stores the new card it rewrites the file, and with `DRIVER_OPTION=auto` a card that does not need the option (for example one whose firmware already gives a BAR1 at least its VRAM) is no longer listed from the next driver load. `record` notes the swap in `/etc/geforce-bar1-resize/replaced` (`card swapped` in the log) until a write of the option file completes, so the old key is dropped also when that rewrite stops (a foreign `NVreg_RegistryDwordsPerDevice` line: rerun with `--adopt-driver-line`) or when `install.sh` runs before the record unit. An explicit `CARDS=` list names addresses only: a card at an address not in it is left alone without a log line; add the address, or set `CARDS=auto`. A migrated install has such a list (from `REBAR_BDFS`) and a global `SIZE=` (from `REBAR_N`), which also applies to a new card at a listed address; set `SIZE=auto` or `size=` for that card if its VRAM differs. `CARD[<address>]` entries with `ids=` are ignored for a card with other ids (`entry ignored` in the log); without `ids=` they apply to whatever card is at that address; `CARD[<ids>]` entries follow the card. |
| `Cannot obtain unbindLock` (`sriov-manage`, e.g. from `geforce-sriov enable`) or `NVRM: ... Could not acquire UnbindLock` right after the driver loads; no VFs | A program had the GPU open while a tool tried to unbind or reconfigure it right after the driver bound. Earlier versions of the record unit did this: its `nvidia-smi` ran at every bind. Now it runs no `nvidia-smi` for a card already recorded with the same ids or for a virtual function, and waits `RECORD_DELAY` seconds (default 60) before it queries a new or changed card, skipping it if it left `nvidia` meanwhile. That query, like `record` without an address (as `install.sh` runs it), covers every GPU the driver holds, so it may still open a recorded card. VF enable and passthrough tools (a VFIO rebind) that run right after the driver loads are no longer raced by the record unit. If it still happens, `sudo fuser -v /dev/nvidia*` shows the holder; run the tool again once it is gone, or raise `RECORD_DELAY` for a card not yet recorded. |
| `already bound to nvidia, skip`, BAR1 stock | The driver bound first. Enable the unit and keep the NVIDIA driver out of the initramfs. |
| `S<k> ...`, then `0x610 route not available` and `route skip: capability lists up to ... < target` | The card does not have the GA102 VSEC layout, and its capability lists no size above its current BAR1. Nothing was written. Please report it with `check --report`. |
| `resize to <X> MiB, the largest size the card lists; below VRAM (<V> MiB)`, then `because ...` | Best effort: the card has no route to the full size, so BAR1 got the largest size its capability lists (more than stock, less than VRAM). Nothing else was written; the card keeps the driver's static BAR1 unless `driver_option=on`. Please report the card with `check --report`. |
| `capability did not widen to ...`, `capability lost sizes it listed before arming`, `0x610 did not latch` | The card did not react as GA102 does; it was disarmed and runs stock. Please report it. |
| `resize failed (No space left on device ...`, then `disarmed, left at stock` or (resize only) `left at its current ... MiB` | Linux could not fit the larger BAR1; the card runs at its previous size. Usually the card sits behind a PCIe switch whose windows the firmware sized for the BARs the cards had at boot ([pcie-switches.md](pcie-switches.md)); otherwise enable Above-4G decoding or enlarge the 64-bit MMIO range in the BIOS. |
| `resize failed (Device or resource busy ...` | The card's SR-IOV virtual functions are enabled, and Linux does not resize a BAR while they are. Resize before enabling them: at boot this is already the order, since `geforce-bar1-resize` runs before the driver. On a running system, disable the VFs first (`echo 0 > /sys/bus/pci/devices/<BDF>/sriov_numvfs`). |
| `gbr_layout: root <port> refuse <BDF> has SR-IOV` (or `would-refuse` in the dry run) | The layout module never lays out a root port with an SR-IOV function: its plan would drop the virtual functions' resources. A card on a CPU root port does not need the module. |
| `resize failed (resize reported success but BAR1 is ... MiB ...` | The kernel accepted the write but BAR1 kept its size; the card runs at its previous size (after `0x610`, disarmed and stock). |
| `... reboot required` | The cards' state is unknown; reboot (everything is volatile). Details in [pcie-switches.md](pcie-switches.md). |
| `old 3080-20gb-rebar files still present` | Run `install.sh` to migrate them ([migration.md](migration.md)). |
| `warning: more than one NVreg_RegistryDwordsPerDevice line` | Only the last line counts. `sudo geforce-bar1-resize driver-option --write --adopt-driver-line` merges them. |
| Host-visible allocations fail at about half of VRAM | The card runs with the driver's static BAR1: `RMForceStaticBar1=0` is written by default only for cards enlarged through `0x610`. For a resize-only card set `driver_option=on` (unless you use P2P that needs static BAR1); check with `sudo geforce-bar1-resize driver-option --print`, then `--write` and reboot ([driver-option.md](driver-option.md)). |
| `warning: RMForceStaticBar1=1 with BAR1 <B> MiB, VRAM <V> MiB: driver <version> may fail to initialize the card`, or `kbusEnableStaticBar1Mapping_TU102: Failed to create the static bar1 mapping` in the kernel log | Static BAR1 is forced for a card whose BAR1 has less than 512 MiB above VRAM (for example a 16 GB RTX 50 card). The static mapping starts at 512 MiB, and from driver 610 the driver reserves less VRAM, so the mapping can run past the end of BAR1 and the card does not initialize. Add `RMIncreaseRsvdMemorySizeMB` to the card's `keys=` ([driver-option.md](driver-option.md#static-bar1-on-a-card-whose-bar1-equals-vram)). The warning is a hint only. |
| `warning: RMForceStaticBar1=1 with BAR1 <B> MiB, VRAM <V> MiB: no driver version can initialize the card`, or `is not large enough to map FB size` in the kernel log | Static BAR1 is forced for a card whose BAR1 is smaller than its VRAM (for example one left at 256 MiB), without `RMIncreaseRsvdMemorySizeMB`. Forced static BAR1 needs BAR1 >= VRAM unless `RMIncreaseRsvdMemorySizeMB` reserves the difference. Remove `RMForceStaticBar1=1` for the card, from its `keys=` or the option file ([driver-option.md](driver-option.md#static-bar1-on-a-card-whose-bar1-equals-vram)). The warning is a hint only. |
| Unbind hangs or the screen goes blank on the display card | Detach the console first ([manual-procedure.md](manual-procedure.md)); at boot see [console.md](console.md). |
| `echo ... > resource1_resize` fails with `EINVAL` | Write the size index, not bytes: `n + 6` (15 for 32 GiB). |
| CPU writes through BAR1 are slow on an idle GPU | The idle GPU lowers its PCIe link speed (on the RTX 3080 20GB, writes fell from about 9.6 GB/s to 5 or 2.4 GB/s). With persistence mode on (`nvidia-smi -pm 1`), lock the memory clock around large uploads: `nvidia-smi -i <BDF> -lmc <max>,<max>`, then `-rmc`. |
